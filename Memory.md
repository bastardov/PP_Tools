# Memory — память по проекту PP_Tools

Подробное знание о плагине. `AGENTS.md` — общие правила, этот файл — конкретика по
инструментам и модулям. Цель: новый агент, прочитав `AGENTS.md` + `Memory.md`, быстро
понимает проект и может работать без перечитывания всех `script.py`.

Как пользоваться:
- Перед доработкой инструмента читать его карточку ниже.
- После изменений обновлять соответствующий раздел.
- Держать только устойчивое знание (что делает инструмент, какие модули `lib` и параметры
  использует, ключевые решения). Не копировать сюда весь код и не писать одноразовые детали.

---

## Общая структура

- Таб: `PP_ОВиК.tab` — единственный таб плагина.
- Панели именуются с числовым префиксом (`01_`, `02_`, …), который задаёт порядок в ленте.
- Каждый инструмент — папка `*.pushbutton` с `script.py`, `icon.png`, обычно `bundle.yaml`.
- Связанные кнопки группируются в `*.stack` (стек из 2 кнопок).
- Порядок кнопок внутри панели может задаваться файлом `layout` (есть в `03_Марки.panel`).
- Общая логика вынесена в `lib/` (см. раздел «Модули lib»).
- Платформа: pyRevit, Revit 2022, IronPython 2.7. Ограничения по синтаксису — в `AGENTS.md`.

## Модули lib

Общие модули, переиспользуемые инструментами. Подключаются из `script.py` (через `sys.path`
pyRevit видит `lib/`).

### `pp_settings.py` + `pp_settings.json`
Чтение/запись настроек плагина. `DEFAULT_SETTINGS` задаёт значения по умолчанию, реальные
значения хранятся в `pp_settings.json`. Используется панелью «Настройки» и инструментами,
которым нужны параметры. Ключевые параметры:
- `show_success_report`, `show_warning_report` — показывать ли отчёты.
- `pipe_pair_distance_mm` (600.0) — расстояние для пары труб.
- `detect_orientation`, `heatloss_show_report` — флаги для теплопотерь/ориентации.
- `mep_transfer_show_pyrevit_report` — показывать подробный pyRevit-отчёт после
  инструмента «Передача параметров по MEP».
- `sheet_name_prefixes` — префиксы имён листов (для «Заполнить имя листа по видам»).
- `sheet_plan_location_map`, `sheet_plan_section_map` — словари формата
  `"ключ = значение"` для «Заполнить имя листа по планам» (локации и разделы).
- `proxy_rule_codes`, `proxy_position_types` — справочники для прокси-контроллера.
- `tag_rules` — таблица правил для «Инструментов меток» (см. `pp_tagrules.py`). Список
  словарей: `cat` (имя BuiltInCategory элемента), `family`, `type` (или null), `tag_family`,
  `tag_type`, `leader`. Стартово засеяны пресеты пользователя (SR, РВ-1, PPK-2… и др.).
- `tag_size_presets`, `tag_size_active` — размерные правила меток (2026-08-20). Пресет:
  `{"name": ..., "rules": [...]}`, строка правила: `cat`, `min_len`, `max_len` (null =
  «и больше»), `tag_family`, `tag_type`. `tag_size_active` — имя пресета, по которому
  работает «Применить по шаблону».

> При добавлении нового параметра: добавить в `DEFAULT_SETTINGS`, при необходимости — в UI
> панели «Настройки», и описать здесь.

**Безопасность файла настроек (2026-08-24).** Формат имеет служебный ключ
`_schema_version` (`SETTINGS_SCHEMA_VERSION` в `pp_settings.py`). Известные ключи при
чтении проверяются по типам значений из `DEFAULT_SETTINGS`; неверный тип заменяется
дефолтом и записывается в `_logs/settings.log`, а импорт файла с неверными типами
отклоняется. Сохранение идёт сначала во временный UTF-8 JSON в той же папке; файл
перечитывается для проверки, затем атомарно заменяет основной через .NET `File.Replace`.
Предыдущая рабочая версия хранится как `pp_settings.json.bak`; вне IronPython работает
восстанавливаемая схема из двух переименований. Повреждённый основной файл не затирается:
он переносится в `pp_settings.invalid_YYYYMMDD_HHMMSS.json`, после чего настройки
восстанавливаются из `.bak`, а если резервной копии нет — из дефолтов. Та же защита
срабатывает при прямом `save_settings()` без предварительного `load_settings()`.

### Автономная проверка проекта

- `.agents/validate_project.py` — единый Python 3 preflight без запуска Revit.
  Проверяет структуру вкладок/панелей/кнопок, обязательную телеметрию, bundle-файлы,
  PNG-иконки, совместимость с IronPython 2.7, синтаксис Python, XAML, ресурсы темы,
  `FindName`/биндинги и восстановление `pp_settings` на временных файлах.
- `.agents/run_checks.bat` запускает preflight через `py -3` или `python`.
- Обычный режим возвращает ненулевой код только для критических ошибок. Накопленное
  наследие (иконки 1024×1024, старые `forms.alert`, bare `except`, строки без `u` и т. п.)
  выводится как замечания. Ключ `--strict` делает замечания блокирующими — его включать
  по мере очистки проекта.
- `.agents/validate_wpf.py` остаётся библиотекой детальных WPF-проверок; разбор AST
  понимает допустимый для IronPython префикс `ur`, который не принимает Python 3.
- Проверка Revit API и поведения транзакций по-прежнему выполняется вручную через
  pyRevit Reload.

### `pp_tagrules.py`
Общая логика инструментов «Инструменты меток» и «Маркировать по правилу». Содержит
`ELEMENT_CATEGORIES` (4 категории: воздухораспределители/арматура возд./оборудование/арматура
труб + соответствующие категории марок `*Tags`). Ключевое:
- `find_rule(rules, cat_enum, family, type)` — поиск правила в два уровня: сначала точное
  `family+type`, затем правило на всё семейство (`type=None`).
- `resolve_tag_symbol(doc, cat_enum, tag_family, tag_type)` — находит `FamilySymbol` марки
  по именам семейства и типа; None, если не загружен в проект.
- `collect_element_types(doc, cat_enum)` / `collect_tag_symbols(doc, cat_enum)` — типы
  элементов и типы марок категории из проекта (для дерева и combo конфигуратора).
- `get_assignment/set_assignment/remove_assignment` — точечная работа с правилом узла.
- `CONFIG_ENUM_NAMES` — какие категории показывает конфигуратор. Сейчас 9:
  воздухораспределители, арматура возд., арматура труб, оборудование, воздуховоды,
  трубы, материалы изоляции труб/возд., обобщённые модели (у каждой своя категория
  марок `*Tags`). Для системных типов (воздуховоды/трубы/изоляция) имя семейства берётся
  из `ElementType.FamilyName`; если пустое — единый ярлык `NO_FAMILY` = «(без семейства)»
  (одинаково в конфигураторе и при применении, чтобы правило совпадало).
- `get_family_name/get_type_name/get_element_category_enum`, `get_location_point`.

**Размерные правила воздуховодов (2026-08-20).** У воздуховодов ширина марки зависит не от
типа элемента, а от длины надписи: «100х100» — 7 знаков, «1000х1000» — 9, «ДВ 10, 1000х500» —
15. Поэтому рядом с `tag_rules` живёт второй вид правил — диапазон длины ПЛЮС область
действия (семейство и тип воздуховода):
- `SIZE_ENUM_NAMES` — только `OST_DuctCurves`. Воздуховодов НЕТ в `CONFIG_ENUM_NAMES`:
  первая вкладка их не показывает, всё настраивается во вкладке «Воздуховоды».
- `measure_tag_text(text)` — длина самой длинной строки надписи. Текст берётся из
  `IndependentTag.TagText`, то есть формат label угадывать не нужно: что нарисовано на виде,
  то и меряем.
- `size_rule_scope(rule)` — область действия строки `(family, type)`; `(None, None)` — все
  воздуховоды. `scope_rank` — насколько строка точная.
- `rules_in_scope(rules, cat, family, type)` — строки, действующие на этот воздуховод, от
  точных к общим: тип → семейство → общая. Та же лестница, что и у `find_rule`.
- `find_size_rule(rules, cat, length, family, type)` — первая подходящая по длине строка
  в этом порядке. `has_size_rules` — есть ли вообще строки под категорию.
- `find_size_overlap(..., family, type)` — пересечение диапазонов проверяется ТОЛЬКО внутри
  одной области, поэтому «круглые 1–7» и «прямоугольные 1–7» уживаются.
- `size_coverage_gaps(rules, cat, family, type)` — непокрытые длины для выбранной области
  (учитывает и общие строки); окно показывает их строкой под списком.
- `strip_size_categories(rules)` — вычищает из `tag_rules` записи категорий, которые теперь
  настраиваются размерными правилами. Вызывается в кнопках 12 и 14: старые правила по
  воздуховодам удаляются (решение 2026-08-20, переносить не стали).
- `normalize_presets/normalize_size_rule/sort_size_rules/active_preset/active_size_rules` —
  чтение и приведение пресетов из настроек. Пустые настройки дают один пустой пресет
  `DEFAULT_PRESET_NAME`. Тип без семейства обнуляется: смысла не имеет.

> Замер делается ОДИН раз, до `ChangeTypeId`. Если у марок разной ширины различается набор
> label, после смены типа текст изменится, и повторный замер начнёт качать тип туда-обратно.

### `pp_tags.py`
Работа с марками (тегами) и их элементами. Содержит белый список категорий
`ALLOWED_CATEGORIES` (воздухораспределители, арматура воздуховодов, оборудование, арматура
трубопроводов) и `ALLOWED_CATEGORY_NAMES`. Хелперы получения элемента по марке
(`get_tagged_element_from_tag` и др.). Основной модуль для панели «Марки».

### `pp_geometry.py`
Геометрические хелперы поверх `Autodesk.Revit.DB`: операции с `XYZ` (`xyz_add`, `xyz_sub`),
получение опорной точки элемента (`get_element_anchor_point`) и т.п. Используется
инструментами, работающими с координатами (опуск, копирование вертикальных трасс, оформление).

### `pp_wall_merge.py`
Объединение кусков одной стены в одну стену (2026-09-02). Ядро кнопки «Объединить стены»
панели «Теплопотери»: разбор выделения на наборы (`plan`) и создание объединённой стены
(`merge`). Про WPF не знает. Каждый кусок считается прямоугольником в системе координат
набора (u — вдоль оси стены в плане, v — абсолютная отметка), объединение прямоугольников
считается по сетке из их координат, контур обводится по границе закрашенных клеток.

### `pp_slab_fill.py`
Заполнение вырезов под колонны в контуре плиты (2026-09-03). Ядро кнопки «Заполнить плиту»
панели «Теплопотери»: разбор (`plan`) и правка эскиза одной плиты (`apply_item`). Про WPF
не знает. Контур читается из `Sketch` плиты, раскладывается на замкнутые петли, вырез
ищется как вогнутая выемка обхода, правка идёт через `SketchEditScope` — id плиты, тип,
параметры и марки сохраняются.

### `pp_leaders.py`
Работа с выносками марок: получение ссылок (`get_first_reference`), состояние конца выноски
(`get_leader_end_condition`: no_leader / free / …). Используется при копировании/сопоставлении
марок, где важно сохранить геометрию выноски.

### `pp_tag_layout.py`
Раскладка марок на виде: поиск наложений и раздвижка (2026-08-31). Ядро кнопки
«Раздвинуть марки», рассчитано на встраивание в другие кнопки панели.

- `collect_tags(doc, view)` — все марки, видимые на виде.
- `measure_boxes(doc, view, tags, movable_ids=None)` — габариты марок БЕЗ выносок.
  Открывает СВОЮ транзакцию-зонд и откатывает её, поэтому вызывать её при уже открытой
  транзакции нельзя. `movable_ids` — какие марки разрешено двигать; остальные попадают
  в расчёт препятствиями.
- `solve(boxes, gap, max_offset, mode, ...)` — чистая математика, про Revit не знает.
  Поэтому окно инструмента пересчитывает предпросмотр на каждое изменение параметров,
  не открывая транзакций.
- `apply_moves(doc, view, boxes, moves, options)` — перестановка голов марок ВНУТРИ уже
  открытой транзакции.
- `spread_tags(doc, view, tags, options)` — всё вместе, со своей транзакцией.
- `mm_to_ft` / `ft_to_mm` / `view_scale` — миллиметры НА ЛИСТЕ ↔ футы модели.
- `size_summary(boxes, view)` — замеренный габарит марки в мм на листе для строки-диагностики
  в окне.
- `leader_segments` / `leaders_cross` / `segment_hits_box` / `segment_push` — геометрия
  выносок в плоскости вида, без Revit API.
- `count_leader_problems(boxes, positions)` — перекрестившиеся выноски и выноски сквозь
  чужой текст.

> Выноски меряются ДО их выключения в зонде: после `HasLeader = False` геометрию уже не
> прочитать. У марок с прикреплённой выноской `GetLeaderEnd` не работает — конец берётся
> по точке расположения маркируемого элемента (`_element_point`).

> В расчёте выноска начинается не в точке головы, а у КРАЯ марки со стороны элемента —
> так её рисует Revit. Если считать от головы, отрезок идёт сквозь собственный текст
> марки, и проверка «выноска сквозь чужой текст» врёт на каждом столбике марок.

> `tag.get_BoundingBox(view)` возвращает габарит ВМЕСТЕ с выноской и для поиска наложений
> не годится. Замер идёт в транзакции-зонде: выноски выключаются, снимается чистый габарит
> текста, транзакция откатывается. Именно откат, а не «выключил → включил обратно»: он
> возвращает выноски, изгибы и `LeaderEndCondition` ровно как были.

> Считаем в плоскости вида (`RightDirection` / `UpDirection`), а не в мировых XYZ — тогда
> инструмент одинаково работает на планах, разрезах и фасадах.

### `pp_param_picker.py` + `pp_param_picker.xaml`
Общее окно выбора имени параметра (2026-08-19). Раньше жило внутри кнопки «Передача
параметров по MEP-соединениям» (`parameter_picker.xaml` + класс `ParameterPickerWindow`),
вынесено в `lib`, чтобы кнопка «Выбрать…» появилась везде, где имя параметра вводится руками.
- Вызов: `pp_param_picker.ask(options, current=..., title=..., subtitle=..., owner=..., empty_text=...)`.
  Возврат — имя параметра или `None` при отказе.
- Элемент списка: строка либо `{u"name": ..., u"display": ...}`. В поле уходит `name`,
  пользователь видит `display` — туда пишут откуда параметр и насколько покрывает выбранные
  категории.
- Про Revit не знает: список готовит инструмент. Поиск фильтрует по `name`, двойной щелчок
  и Enter выбирают, Esc закрывает. `owner` — вызвавшее окно (иначе главное окно Revit).
- Принцип: кнопка ставится РЯДОМ с полем ручного ввода, а не вместо него — встроенные и
  семейные параметры в списки привязок не попадают, их всё равно вводят руками.
- Подключён в: «Передача параметров по MEP-соединениям», «Окрасить рандомно»
  (через ключ `choice.picker` в `pp_paint_dialog`), «Проверка спецификации»,
  «Проверка Модели», «Проверка теплопотерь» (через `option_type=u"param"`).

### `pp_param_source.py`
Единственное место, где список параметров собирается из модели (2026-08-19). Нужен, чтобы
`pp_param_picker` остался Revit-независимым, а инструменты не повторяли обход привязок.
- `project_parameters(doc)` → `имя -> {u"instance": set(id категорий), u"type": set(...)}`
  по `doc.ParameterBindings`.
- `project_options(doc, category_ids=None, instance_only=False)` → готовые строки для
  `pp_param_picker`: `ADSK_Группирование    · экземпляр / тип · 2 категории`.
  `category_ids` меняет хвост на «есть у N из M выбранных категорий» и поднимает полные наверх.
  `instance_only=True` убирает привязки типа — для инструментов, читающих значение через
  `LookupParameter` у экземпляра (иначе показали бы параметр, который они не прочитают).
- Встроенные и семейные параметры в привязки НЕ попадают: поэтому кнопка «Выбрать…» всегда
  дополняет поле ручного ввода, а не заменяет его.

## Панели и инструменты

Карточки сгруппированы по панелям. Шаблон карточки инструмента — в конце файла.

### 01_Инфо
- **Инфо** — информация о плагине (`script.py`, `icon.png`, `logo.png`). Справочная кнопка.

### 02_Настройки
- **Настройки** — UI настроек плагина. Читает/пишет через `pp_settings`. Точка управления
  всеми параметрами из `pp_settings.json`. Вкладка «Проверка» содержит настройки инструментов
  панели проверки, включая показ pyRevit-отчёта для передачи параметров по MEP.

### 03_Марки
Панель работы с марками. Опирается на `pp_tags`, `pp_leaders`, `pp_geometry`. Два стека.
Порядок кнопок задан тремя файлами сразу (`bundle.yaml` с ключом `layout:`, `_layout`, `layout`) —
имена в них = имена папок С числовым префиксом, без расширения; не перечисленные элементы не создаются.
Текущий порядок (после переноса «Сопоставить труб и возд.» к группе «Сопоставить», 2026-06-30):
- **01_Сопоставить** — сопоставление марок.
- **02_stack2.stack**: Сопоставить по семейству / Сопоставить по типу.
- **03_Сопоставить_марки_воздуховодов_труб** — перенесена сюда (была 11-й).
- **04_Копировать по типу**, **05_Копировать по семейству**.
- **06_Копировать марки для пары труб** — учитывает `pipe_pair_distance_mm`.
- **07_Копировать марки труб**.
- **08_Применить тип марки от эталона**.
- **09_stack3.stack**: Применить тип марки по типу / по семейству (переименован из stack2 в stack3 — имена стеков в одной панели лучше держать уникальными).
- **10_Копировать вертикальные воздуховоды и трубы авто**, **11_… (ручной)**.

- **Проверка №3 в Проверке спецификации** — поле `bzero_text` теперь хранит список запрещенных фрагментов через `;` (логика ИЛИ): например `b=0 мм; класс герметичности ,`. - **02_PP_Передача параметров по MEP-соединениям** (⚠ 2026-07-22 перенесён в панель «06_Рабочие инструменты»; описание оставлено здесь) — универсальный перенос параметра между подключенными MEP-элементами. В окне инструмента пользователь выбирает категории источника и приемника из четырех вариантов: трубы, соединительные детали трубопроводов, арматура трубопроводов и оборудование, затем задает имя параметра источника и приемника. Рядом с обоими полями есть кнопка «Выбрать…» (2026-08-19 окно выбора вынесено в общий `lib/pp_param_picker`, локальный `parameter_picker.xaml` из папки кнопки убран в BACKUPS): список строится из `doc.ParameterBindings` и показывает только параметры проекта, связанные хотя бы с одной выбранной категорией; полное покрытие выбранных категорий поднимается вверх списка. Для источника доступны привязки экземпляра и типа, для приемника — только экземпляра, потому что инструмент не изменяет параметры типоразмера. Ручной ввод сохранен для встроенных и семейных параметров, отсутствующих в параметрах проекта. Режим обработки выбирается из четырех вариантов: «Вся модель», «Текущий вид», «Источник вручную», «Приёмник вручную». При ручном выборе источника Revit разрешает выбрать только элементы выбранных категорий источника; дальше приемники собираются только из напрямую подключенных к этим источникам элементов выбранных категорий приемника. При ручном выборе приемника Revit разрешает выбрать только элементы выбранных категорий приемника; источники при этом ищутся по их коннекторам. Скрипт смотрит только напрямую подключенные элементы через коннекторы Revit и переносит значение, если найден один источник или несколько источников с одинаковым значением. Если найдены разные значения, элемент попадает в конфликт; если заполненный источник не найден, элемент попадает в отчет «источник не найден». Значение источника читается сначала у экземпляра, затем у типа. Запись выполняется только в параметр экземпляра приемника, чтобы не менять сразу все элементы типоразмера. Стартовая конфигурация окна: источник = трубы, приемник = арматура трубопроводов, параметр = `ADSK_Имя системы сокращенное`. Последние имена параметров и выбранный режим сохраняются в `pp_settings.json` в ключе `mep_param_transfer_settings` (`mode`). Подробный вывод в окно pyRevit управляется настройкой `mep_transfer_show_pyrevit_report` на вкладке «Проверка» в инструменте «Настройки»; итоговая белая сводка показывается всегда.

  - 3D-вид без подрезки (`CropBoxActive=False`) помечается в списке и отчёте,

  - Нумерация: `Run.next_number` — подряд от стартового, занятые пропускаются;
    стартовый по умолчанию = max(N среди «N<суффикс>») + 1.
  - Раздел пишется и в лист, и в рамку (`set_section`) — где параметр найдётся.
  - Настройки: `sheet_place_settings` {mode, margins, gap, suffix, orientation
    (landscape/portrait/any; старый ключ portrait читается как any/landscape),
    prefix, sample_id}; `prefix=None` — ещё не выбирали, `""` — «без начала».
  - Масштаб видов не трогается.

- **03_Оси связей в шаблоне** — полуавтомат на UI Automation (внешний
  `uia_worker.ps1`): снимает категорию «Оси» в параметрах отображения связи.
  Revit 2022 не даёт API для покатегорийных настроек связей. Лог:
  `_logs/link_axes_uia.log`.
- **04_Связи в шаблоне** — пакетно задаёт видимость RVT-связей (вкладка
  «Связанные файлы RVT» в В/Г) сразу для многих шаблонов видов ИЛИ обычных видов.
  - Ключевой факт: галочка видимости связи — это обычное скрытие элемента в виде,
    поэтому работает через API (`View.HideElements` / `View.UnhideElements`),
    **в том числе для шаблонов видов** — UIA не нужен. Покатегорийные настройки
    внутри связи (см. инструмент 03) API по-прежнему не поддерживает.
  - **Грабли Revit 2022:** у `View` НЕТ метода `IsElementHidden` (ошибка
    `'View3D' object has no attribute 'IsElementHidden'`). Состояние читается
    через `Element.IsHidden(View)`.
  - Связь выключается ЦЕЛИКОМ: скрывается и `RevitLinkType` (верхняя строка-галочка
    в В/Г), и все его `RevitLinkInstance` (вложенные строки). Если скрыть только
    экземпляры, верхняя галочка в диалоге остаётся стоять. Группировка — класс
    `LinkEntry` (тип + экземпляры), правый список = один пункт на файл связи.
  - **Модель UI (важно, была переделана):** слева — «к чему применяем»
    (`TabControl`: вкладки «Шаблоны видов» и «Виды»), справа — ЖЕЛАЕМОЕ СОСТОЯНИЕ
    связей, а не выбор: галочка стоит → связь видна, галочка снята → связь
    скрывается. Первая версия трактовала правый список как «выбор связей» и
    ругалась «Не выбрана ни одна связь» — так неправильно.
  - Вкладка «Виды» нужна для видов, где шаблон = «нет» (иначе каждый вид вручную).
    Кнопка «Текущий вид» отмечает активный вид. Если у обработанного вида назначен
    шаблон, он попадает в отчёт с предупреждением, что шаблон перебьёт изменения.
  - Кнопка «Как в текущем виде» подтягивает фактическое состояние связей активного
    вида в правый список (и это же состояние — дефолт при первом запуске).
  - Класс `FilteredCheckList` — переиспользуемая пара «строка поиска +
    `CheckedListBox`»; галочки при фильтрации не теряются (набор имён в

  - Имена: только через `Element.Name.GetValue(el)` (`elem_name`), иначе у
    `RevitLinkInstance` вылезает длинное `файл.rvt : 12 : позиция ...`.

  - Фильтр видов/шаблонов: исключены Schedule, ColumnSchedule, PanelSchedule,
    DrawingSheet, Legend, Report, SystemBrowser, ProjectBrowser, Internal, Undefined.
  - Конфиг pyRevit: `saved_templates`, `saved_views`, `saved_visible_links`.
  - Всё одной транзакцией; проблемные виды и виды с шаблоном — в отчёт output.
  - Итоговое окно — через `show_report` из `pp_settings`, как у остальных

### 11_Статистика
- **01_Статистика использования** — счётчик запусков инструментов плагина.
  - **Механизм: СВОЯ телеметрия (`lib/pp_usage.py`), встроенная телеметрия pyRevit
    больше не используется.** Отказались от неё 2026-07-20: она создавала файл на
    каждую сессию (67 файлов), но реальных записей почти не писала, логировала чужой
    `pyRevitCore`, а путь к папке сохраняла экранированным и молча отключалась.
  - Универсального хука «на любую кнопку» в pyRevit НЕТ (есть только
    `command-before-exec[<id>]` по конкретному id), поэтому вызов явный: в начало
    каждого `script.py` вставлена защищённая строка

        try: import pp_usage; pp_usage.log(__file__)
        except Exception: pass

    Она стоит сразу после строки кодировки. `pp_usage.log()` никогда не бросает
    исключений — сбой логирования не должен ронять инструмент.
  - **Формат: append-only JSONL** — `telemetry/pp_usage_YYYY-MM.jsonl` (одна
    JSON-запись на строку, файл на месяц). Выбран намеренно: дописывание строки
    атомарно, несколько сессий Revit не портят файл, битая строка не убивает весь
    лог (в отличие от единого JSON-массива, который вёл pyRevit).
  - Поля записи: `ts` / `date` / `time` (локальное время), `tool` (имя без префикса
    «06_»), `bundle`, `panel`, `tab`, `user` (**имя пользователя из настроек Revit**,
    через `HOST_APP.username`), `winuser`, `revit`, `doc`.
  - Разбор пути кнопки идёт вверх по дереву и корректно понимает кнопки внутри
    `.stack` (панель находится через уровень).
  - Кнопка статистики читает `pp_usage.read_records()` и показывает WinForms
    `ListView` с переключателем группировки: по инструментам / по пользователям /
    по инструментам и пользователям. Есть «Экспорт в CSV» (utf-8-sig, разделитель `;`).
  - **Правило для новых кнопок:** при создании любой новой кнопки обязательно
    добавлять строку `pp_usage.log(__file__)` — иначе её запуски не попадут в учёт.
  - **Хранение:** `telemetry/` внутри расширения; периодическая выгрузка на сервер
    (xpenology) — `export_telemetry.bat` (robocopy по маске `pp_usage_*.jsonl`) в
    корне расширения, ставится в Планировщик задач Windows (заменить `DST`).
  - Учёт ведётся с момента установки этой версии; задним числом данных нет.
  - **Грабля чтения (2026-07-24):** нельзя читать JSONL лениво через
    `for line in io.open(path, encoding="utf-8")` — в IronPython построчное чтение
    utf-8 с кириллицей срывается посреди файла с исключением. Если это исключение
    ловить на уровне ВСЕГО файла, теряются все строки после сбоя (симптом: в
    статистике видно только первые 1–2 записи, хотя в файле их сотни). Правильно:
    читать файл целиком в бинарном режиме (`io.open(path, "rb").read()`), декодировать
    самим (`raw.decode("utf-8-sig", "replace")`), бить на строки в памяти и парсить
    каждую в отдельном try/except. Сделано в `pp_usage._read_text` / `read_records`.
  - **Важно:** новая панель/кнопка появится в ленте только после
    `pyrevit caches clear --all` + запуск Revit (Reload не пересобирает ленту).
    Правки внутри `script.py` подхватываются сразу, без Reload.

## Принятые решения и нюансы

В WinForms-окнах размер задавать через `ClientSize`, а НЕ через `Size`.
`Size` — это размер окна целиком, включая заголовок и рамки (~40 px по высоте),
поэтому элементы, позиционированные у нижнего края (кнопки, подписи), обрезаются
границей окна. Правильно: `self.ClientSize = Size(w, h)` и все координаты считать
от `w`/`h`, например `btn_y = h - PAD - BTN_H`. `MinimumSize` при этом остаётся
размером окна — его берут с запасом. Наступили на это в «Статистика использования»
(2026-07-20), кнопки «Экспорт в CSV» и «Закрыть» оказались срезаны.


- Резервное копирование перед изменениями — обязательно (см. `AGENTS.md` → «Резервное копирование»).
- При правке Revit API проверяется вручную через pyRevit Reload.
- **Перестановка кнопок в панели (важно, проверено 2026-06-30):** порядок применяется только при создании ленты с нуля. pyRevit Reload создаёт кнопки с `update_if_exists=True` — обновляет существующие «на месте», НЕ переставляя; `sort_pyrevit_ui` переупорядочивает только панели, не кнопки внутри панели. Переименование папки кнопки двигает её при Reload (меняется unique_name → пересоздаётся), но переименование стека/правка `layout` — нет.
- **Главный нюанс:** структура расширения кэшируется pyRevit в `%APPDATA%\pyRevit\`. После правок раскладки (layout, стеки) одного Reload и даже полного перезапуска Revit мало — нужно очистить кэш: `pyrevit caches clear --all`, затем открыть Revit. Симптом устаревшего кэша — заголовок панели «прыгает» между `03_Марки` и `03 Марки`.
- Стек (`*.stack`) объединяет 2 кнопки вертикально — соблюдать при добавлении кнопок в группу.
- Иконки — строго по `ICONS.md` (32×32, PNG, прозрачный фон, имя `icon`).


### Теплопотери / Объединить стены
- Назначение: архитектор рисует одну стену кусками (простенок, перемычка над проёмом,
  сегменты в ряд), и в расчёте теплопотерь каждый кусок даёт свою позицию. Кнопка
  собирает куски в одну стену. Работает итеративно: результат снова годится на вход,
  так набирается вся стена фасада.
- Вход: выделенные стены (без выделения — `PickObjects` с фильтром по категории «Стены»).
  Тип объединённой стены выбирается в окне: «Автоматически» (тип самого большого куска)
  либо конкретный тип из выделения — так объединяются куски с разными именами типов,
  но одинаковым пирогом.
- Логика:
  1. Отсев непригодных: витраж, составная стена, стена в группе, дуга, проёмы
     (`FindInserts`), привязка верха/низа, неступенчатый контур грани.
  2. Контур каждого куска снимается с ГЕОМЕТРИИ: `wall_contours` берёт все грани,
     лежащие в одной плоскости и смотрящие наружу, у каждой — все контуры
     (`GetEdgesAsCurveLoops`, запасной путь `EdgeLoops`).
  3. Группировка по плоскости: канонизированное направление оси в плане + смещение
     линии привязки, округлённое до миллиметра.
  4. Объединение: общая сетка из всех координат контуров; клетка закрашена, если её
     середина внутри любого куска (чётность попаданий в контуры одной грани — так
     вырез остаётся вырезом). Дальше связные компоненты, проверка дырки, обводка
     границы, снятие точек на прямых участках.
  5. Создание: прямоугольник — `Wall.Create` по линии, любая другая форма —
     `Wall.Create` по профилю с нормалью самого большого куска.
  6. `_enforce_height` сверяет габариты готовой стены с расчётным контуром.
- Модули lib: `pp_wall_merge` (всё ядро), `pp_wpf`, `pp_settings.show_report`, `pp_usage`.
- Параметры: своих ключей в `pp_settings.json` нет; показ отчёта — общий
  `show_success_report` / `show_warning_report`.
- Нюансы/решения:
  * **Габариты только с геометрии.** Параметры «Зависимость/Смещение снизу-сверху»
    описывают зависимости, а не тело: у перемычки над проёмом с изменённым профилем
    они говорят «от пола до уровня выше». Первая версия читала их — объединение
    схлопывалось в сплошной прямоугольник поверх окна. Смещения к тому же
    ОТНОСИТЕЛЬНЫЕ, у каждого куска свои: складывать и наследовать нельзя.
  * **Кусок не обязан быть прямоугольником** — требуется лишь ступенчатый контур.
    Иначе уже объединённая Г/П-образная стена не проходит на второй итерации.
  * **Грань стены приходит не одной пластиной**: несколько компланарных частей плюс
    возможные вырезы. Читать надо все.
  * **Исходные куски удаляются ДО создания новой стены**, иначе Revit показывает
    диалог «стены накладываются». Параметры снимаются в словарь заранее
    (`_read_params`) и пишутся в новую стену после (`_write_params`).
  * Переносятся параметры проекта и общие (`Id.IntegerValue >= 0`) плюс явно фаза
    создания/сноса и рабочий набор. Имя типа — только через `element_name`.
  * Новая стена рождается по осевой, а у наружных стен модели линия привязки
    «Чистовая поверхность: Внутренняя» — поэтому сдвиг по нормали через сравнение
    середин габаритов (`_center_offset`) обязателен.
  * Каждый набор — своя `SubTransaction`: отказ по одному не роняет остальные.
  * **Окна и двери** переносятся по выключенной по умолчанию галочке «Переносить
    проёмы»: Revit не умеет менять окну хост, поэтому они вставляются заново и
    получают новые id (параметры проекта, марка, фаза, рабочий набор — переносятся,
    марки-выноски теряются). Галочка меняет сам разбор, поэтому окно просит скрипт
    пересчитать его на лету колбэком `replan(move_inserts)`.
  * **Контур грани приходит уже с вырезом под проём**, поэтому в режиме переноса
    габариты проёмов подмешиваются к контуру (`_insert_boxes`) — иначе вставленная
    дверь ничего не режет, а оконная дырка отбивает набор.
  * **Витраж (встроенная стена) НЕ удаляется вместе с host-стеной** — это
    самостоятельный элемент. Его след заращивается, а после объединения он врезается
    в новую стену через `SolidSolidCutUtils.AddCutBetweenSolids`. Галочки не требует.
    Неудачная врезка не роняет объединение, уходит замечанием в отчёт.
  * **Урок отладки:** голые `except: return None` в геттерах геометрии стоили двух
    кругов переписки. В окне ошибки печатается traceback, причина отказа несёт текст
    исключения, а в окне под каждым набором перечислены его куски с размерами.


### Теплопотери / Заполнить плиту
- Назначение: пол или кровля, нарезанные по пространствам, повторяют границу помещения и
  обходят колонны «зубцом». Кнопка убирает эти вырезы из контура, чтобы плита была ровной.
  Создана 2026-09-03, кнопка `09_Заполнить плиту` панели «Теплопотери».
- Вход: выделенные полы и кровли (без выделения — `PickObjects` по категориям
  «Перекрытия» и «Крыши»). Условия поиска в окне: выемка с колонной, выемка мельче порога
  (мм), отверстия внутри плиты. Любое изменение условий пересчитывает разбор колбэком
  `replan(options)` — как в «Объединить стены».
- Логика:
  1. Контур берётся из `Sketch` плиты (`SketchId`, запасной путь —
     `GetDependentElements(ElementClassFilter(Sketch))`), кривые сцепляются в петли по
     совпадению концов, каждая петля разворачивается против часовой стрелки и начинается
     с крайней вершины — так вырез никогда не «заворачивается» через нулевую кривую.
  2. Внешние петли и отверстия разделяются проверкой «точка внутри другой петли».
  3. Вырез — участок из 2–6 ПРЯМЫХ кривых, у которого концы участка выпуклые, внутри есть
     хотя бы одна вогнутая вершина, а замыкающая хорда добавляет площадь и не пересекает
     остальной контур. Дуги не трогаются.
  4. Габарит выреза меряется и по осям хорды, и по осям плана — берётся меньшее
     (`pocket_size_mm`): вырез в углу закрывается диагональю и по хорде выглядит крупнее,
     чем есть.
  5. Заполняется, если в вырезе стоит колонна (модель + RVT-связи, габарит в плане и
     отметка) ИЛИ вырез мельче порога. По колонне действует дополнительный ограничитель:
     вырез не больше самой колонны плюс 250 мм — настоящий уступ плиты не тронется.
  6. Правка (`build_edits`): соседнее ребро продлевается, если оно на одной прямой с
     другим соседом; если соседи сходятся — оба ведутся до их общего угла (вырез в углу
     здания); иначе создаётся новая линия-хорда. Так у оставшихся рёбер сохраняются их
     параметры (у кровли — уклон и смещения).
  7. `apply_item` открывает `SketchEditScope`, внутри одной транзакции удаляет кривые
     выреза, правит `GeometryCurve` соседей и добавляет новые линии
     (`doc.Create.NewModelCurve`), затем `scope.Commit` с гасителем предупреждений.
     Скрипт оборачивает все плиты в `TransactionGroup` + `Assimilate` — отмена одним
     Ctrl+Z.
- Модули lib: `pp_slab_fill` (всё ядро), `pp_wpf`, `pp_settings.show_report`, `pp_usage`.
- Параметры: свои ключи только в конфиге pyRevit `pp_slab_fill`
  (`by_column`, `by_size`, `max_mm`, `fill_holes`); в `pp_settings.json` ничего не пишет.
- Нюансы/решения:
  * **Почему не пересоздание плиты.** `SketchEditScope` (появился в Revit 2022) правит
    эскиз существующего элемента: id, тип, параметры, марки и размеры остаются. Кровлю
    пересоздать вообще нечем без потери уклонов.
  * **Критерий «концы участка выпуклые».** Без него вырез срезается по диагонали:
    подходит и кусок настоящего выреза (треугольник от входа до внутреннего угла), и он
    находится первым как самый короткий.
  * **Кровля выдавливанием** пропускается: у неё нет контура-эскиза, причина пишется в
    окно и в отчёт.
  * Проверено на синтетических контурах (вырез в середине стены, вырез в углу, два выреза
    подряд рядом с настоящим уступом 4×2 м, выемка крупнее порога, колонна на другой
    отметке) — заглушки Revit API в `$HOME/pp_test` вне репозитория.

### Теплопотери / Переставить стор. света
- Назначение: здание развернули (или поменяли угол к северу) — записанные стороны света
  разом стали неверными. Кнопка не считает их заново, а сдвигает готовые значения по
  кругу на выбранный угол. Создана 2026-09-03, кнопка `10_Переставить сторону света`
  панели «Теплопотери».
- Вход: выделять ничего не нужно. Берутся стены, витражи, окна и двери АКТИВНОГО 3D вида
  (`FilteredElementCollector(doc, view.Id)` — разрезающая рамка и фильтры вида работают
  как отбор) с непустым `PP_Ориентация по стороне света`. Не 3D вид или шаблон — окно
  с просьбой открыть 3D.
- Логика:
  1. Значение нормализуется: `strip().upper()` плюс замена латинских двойников
     (`C→С`, `B→В`, `3→З`, `E→Е`, `O→О`). Всё, что не попало в список из восьми сторон,
     считается нераспознанным и в отчёте выводится числом.
  2. Окно показывает два компаса. Левый — как записано, с числом элементов у каждой
     буквы; правый — та же роза, повёрнутая по часовой стрелке на выбранный угол.
     Соглашение: буква с позиции `j` уезжает на позицию `j + steps`, поэтому на позиции
     `i` рисуется `SECTORS[(i - steps) % 8]`, а новое значение = `SECTORS[(j + steps) % 8]`.
     Это ровно то, что происходит с розой, приклеенной к повёрнутому зданию.
  3. Угол задаётся чипсами 0…315° и кнопками ⟲/⟳ (шаг 45°). Итог в `Card.Result` —
     число элементов и карта переноса только по тем сторонам, которые реально есть.
  4. Запись в одной транзакции, только `PP_Ориентация по стороне света`.
- Модули lib: `pp_wpf`, `pp_settings.show_report`, `pp_usage`. Своего модуля в `lib` нет:
  вся геометрия отсутствует, окно лежит рядом со скриптом
  (`pp_compass_shift_window.py` + `ui.xaml`).
- Параметры: ничего не сохраняет — угол каждый раз выбирается заново, чтобы случайно не
  применить старый поворот.
- Нюансы/решения:
  * **Добавка по умолчанию не трогается.** Решение пользователя: инструмент меняет только
    текст ориентации. Галочка «Заодно пересчитать `PP_Добавка на сторону света`» выключена
    и берёт ту же таблицу `ORIENT_COEFF`, что и «Опр. стор. света» — при правке
    коэффициентов править обе кнопки.
  * **Не замена «Опр. стор. света».** Кнопка годится, когда повернули здание целиком;
    для отдельных стен нужен пересчёт зондами.
  * Годится и как ручная правка: витражи, которым «Опр. стор. света» проставил сторону
    через `fallback-2D`, можно переставить пачкой, не трогая остальные.
