# Memory — память по проекту PP_Tools

Подробное знание о плагине. `AGENTS.md` — общие правила, этот файл — конкретика по
инструментам и модулям. Цель: новый агент, прочитав `AGENTS.md` + `Memory.md`, быстро
понимает проект и может работать без перечитывания всех `script.py`.

Как пользоваться:
- Перед доработкой инструмента читать его карточку ниже.
- После изменений обновлять соответствующий раздел.
- Держать только устойчивое знание (что делает инструмент, какие модули `lib` и параметры
  использует, ключевые решения). Не копировать сюда весь код и не писать одноразовые детали.

---

## Общая структура

- Таб: `PP_ОВиК.tab` — единственный таб плагина.
- Панели именуются с числовым префиксом (`01_`, `02_`, …), который задаёт порядок в ленте.
- Каждый инструмент — папка `*.pushbutton` с `script.py`, `icon.png`, обычно `bundle.yaml`.
- Связанные кнопки группируются в `*.stack` (стек из 2 кнопок).
- Порядок кнопок внутри панели может задаваться файлом `layout` (есть в `03_Марки.panel`).
- Общая логика вынесена в `lib/` (см. раздел «Модули lib»).
- Платформа: pyRevit, Revit 2022, IronPython 2.7. Ограничения по синтаксису — в `AGENTS.md`.

## Модули lib

Общие модули, переиспользуемые инструментами. Подключаются из `script.py` (через `sys.path`
pyRevit видит `lib/`).

### `pp_settings.py` + `pp_settings.json`
Чтение/запись настроек плагина. `DEFAULT_SETTINGS` задаёт значения по умолчанию, реальные
значения хранятся в `pp_settings.json`. Используется панелью «Настройки» и инструментами,
которым нужны параметры. Ключевые параметры:
- `show_success_report`, `show_warning_report` — показывать ли отчёты.
- `pipe_pair_distance_mm` (600.0) — расстояние для пары труб.
- `detect_orientation`, `heatloss_show_report` — флаги для теплопотерь/ориентации.
- `mep_transfer_show_pyrevit_report` — показывать подробный pyRevit-отчёт после
  инструмента «Передача параметров по MEP».
- `sheet_name_prefixes` — префиксы имён листов (для «Заполнить имя листа по видам»).
- `sheet_plan_location_map`, `sheet_plan_section_map` — словари формата
  `"ключ = значение"` для «Заполнить имя листа по планам» (локации и разделы).
- `proxy_rule_codes`, `proxy_position_types` — справочники для прокси-контроллера.
- `tag_rules` — таблица правил для «Инструментов меток» (см. `pp_tagrules.py`). Список
  словарей: `cat` (имя BuiltInCategory элемента), `family`, `type` (или null), `tag_family`,
  `tag_type`, `leader`. Стартово засеяны пресеты пользователя (SR, РВ-1, PPK-2… и др.).
- `tag_size_presets`, `tag_size_active` — размерные правила меток (2026-08-20). Пресет:
  `{"name": ..., "rules": [...]}`, строка правила: `cat`, `min_len`, `max_len` (null =
  «и больше»), `tag_family`, `tag_type`. `tag_size_active` — имя пресета, по которому
  работает «Применить по шаблону».

> При добавлении нового параметра: добавить в `DEFAULT_SETTINGS`, при необходимости — в UI
> панели «Настройки», и описать здесь.

**Безопасность файла настроек (2026-08-24).** Формат имеет служебный ключ
`_schema_version` (`SETTINGS_SCHEMA_VERSION` в `pp_settings.py`). Известные ключи при
чтении проверяются по типам значений из `DEFAULT_SETTINGS`; неверный тип заменяется
дефолтом и записывается в `_logs/settings.log`, а импорт файла с неверными типами
отклоняется. Сохранение идёт сначала во временный UTF-8 JSON в той же папке; файл
перечитывается для проверки, затем атомарно заменяет основной через .NET `File.Replace`.
Предыдущая рабочая версия хранится как `pp_settings.json.bak`; вне IronPython работает
восстанавливаемая схема из двух переименований. Повреждённый основной файл не затирается:
он переносится в `pp_settings.invalid_YYYYMMDD_HHMMSS.json`, после чего настройки
восстанавливаются из `.bak`, а если резервной копии нет — из дефолтов. Та же защита
срабатывает при прямом `save_settings()` без предварительного `load_settings()`.

### Автономная проверка проекта

- `.agents/validate_project.py` — единый Python 3 preflight без запуска Revit.
  Проверяет структуру вкладок/панелей/кнопок, обязательную телеметрию, bundle-файлы,
  PNG-иконки, совместимость с IronPython 2.7, синтаксис Python, XAML, ресурсы темы,
  `FindName`/биндинги и восстановление `pp_settings` на временных файлах.
- `.agents/run_checks.bat` запускает preflight через `py -3` или `python`.
- Обычный режим возвращает ненулевой код только для критических ошибок. Накопленное
  наследие (иконки 1024×1024, старые `forms.alert`, bare `except`, строки без `u` и т. п.)
  выводится как замечания. Ключ `--strict` делает замечания блокирующими — его включать
  по мере очистки проекта.
- `.agents/validate_wpf.py` остаётся библиотекой детальных WPF-проверок; разбор AST
  понимает допустимый для IronPython префикс `ur`, который не принимает Python 3.
- Проверка Revit API и поведения транзакций по-прежнему выполняется вручную через
  pyRevit Reload.

### `pp_tagrules.py`
Общая логика инструментов «Инструменты меток» и «Маркировать по правилу». Содержит
`ELEMENT_CATEGORIES` (4 категории: воздухораспределители/арматура возд./оборудование/арматура
труб + соответствующие категории марок `*Tags`). Ключевое:
- `find_rule(rules, cat_enum, family, type)` — поиск правила в два уровня: сначала точное
  `family+type`, затем правило на всё семейство (`type=None`).
- `resolve_tag_symbol(doc, cat_enum, tag_family, tag_type)` — находит `FamilySymbol` марки
  по именам семейства и типа; None, если не загружен в проект.
- `collect_element_types(doc, cat_enum)` / `collect_tag_symbols(doc, cat_enum)` — типы
  элементов и типы марок категории из проекта (для дерева и combo конфигуратора).
- `get_assignment/set_assignment/remove_assignment` — точечная работа с правилом узла.
- `CONFIG_ENUM_NAMES` — какие категории показывает конфигуратор. Сейчас 9:
  воздухораспределители, арматура возд., арматура труб, оборудование, воздуховоды,
  трубы, материалы изоляции труб/возд., обобщённые модели (у каждой своя категория
  марок `*Tags`). Для системных типов (воздуховоды/трубы/изоляция) имя семейства берётся
  из `ElementType.FamilyName`; если пустое — единый ярлык `NO_FAMILY` = «(без семейства)»
  (одинаково в конфигураторе и при применении, чтобы правило совпадало).
- `get_family_name/get_type_name/get_element_category_enum`, `get_location_point`.

**Размерные правила воздуховодов (2026-08-20).** У воздуховодов ширина марки зависит не от
типа элемента, а от длины надписи: «100х100» — 7 знаков, «1000х1000» — 9, «ДВ 10, 1000х500» —
15. Поэтому рядом с `tag_rules` живёт второй вид правил — диапазон длины ПЛЮС область
действия (семейство и тип воздуховода):
- `SIZE_ENUM_NAMES` — только `OST_DuctCurves`. Воздуховодов НЕТ в `CONFIG_ENUM_NAMES`:
  первая вкладка их не показывает, всё настраивается во вкладке «Воздуховоды».
- `measure_tag_text(text)` — длина самой длинной строки надписи. Текст берётся из
  `IndependentTag.TagText`, то есть формат label угадывать не нужно: что нарисовано на виде,
  то и меряем.
- `size_rule_scope(rule)` — область действия строки `(family, type)`; `(None, None)` — все
  воздуховоды. `scope_rank` — насколько строка точная.
- `rules_in_scope(rules, cat, family, type)` — строки, действующие на этот воздуховод, от
  точных к общим: тип → семейство → общая. Та же лестница, что и у `find_rule`.
- `find_size_rule(rules, cat, length, family, type)` — первая подходящая по длине строка
  в этом порядке. `has_size_rules` — есть ли вообще строки под категорию.
- `find_size_overlap(..., family, type)` — пересечение диапазонов проверяется ТОЛЬКО внутри
  одной области, поэтому «круглые 1–7» и «прямоугольные 1–7» уживаются.
- `size_coverage_gaps(rules, cat, family, type)` — непокрытые длины для выбранной области
  (учитывает и общие строки); окно показывает их строкой под списком.
- `strip_size_categories(rules)` — вычищает из `tag_rules` записи категорий, которые теперь
  настраиваются размерными правилами. Вызывается в кнопках 12 и 14: старые правила по
  воздуховодам удаляются (решение 2026-08-20, переносить не стали).
- `normalize_presets/normalize_size_rule/sort_size_rules/active_preset/active_size_rules` —
  чтение и приведение пресетов из настроек. Пустые настройки дают один пустой пресет
  `DEFAULT_PRESET_NAME`. Тип без семейства обнуляется: смысла не имеет.

> Замер делается ОДИН раз, до `ChangeTypeId`. Если у марок разной ширины различается набор
> label, после смены типа текст изменится, и повторный замер начнёт качать тип туда-обратно.

### `pp_tags.py`
Работа с марками (тегами) и их элементами. Содержит белый список категорий
`ALLOWED_CATEGORIES` (воздухораспределители, арматура воздуховодов, оборудование, арматура
трубопроводов) и `ALLOWED_CATEGORY_NAMES`. Хелперы получения элемента по марке
(`get_tagged_element_from_tag` и др.). Основной модуль для панели «Марки».

### `pp_geometry.py`
Геометрические хелперы поверх `Autodesk.Revit.DB`: операции с `XYZ` (`xyz_add`, `xyz_sub`),
получение опорной точки элемента (`get_element_anchor_point`) и т.п. Используется
инструментами, работающими с координатами (опуск, копирование вертикальных трасс, оформление).

### `pp_leaders.py`
Работа с выносками марок: получение ссылок (`get_first_reference`), состояние конца выноски
(`get_leader_end_condition`: no_leader / free / …). Используется при копировании/сопоставлении
марок, где важно сохранить геометрию выноски.

### `pp_param_picker.py` + `pp_param_picker.xaml`
Общее окно выбора имени параметра (2026-08-19). Раньше жило внутри кнопки «Передача
параметров по MEP-соединениям» (`parameter_picker.xaml` + класс `ParameterPickerWindow`),
вынесено в `lib`, чтобы кнопка «Выбрать…» появилась везде, где имя параметра вводится руками.
- Вызов: `pp_param_picker.ask(options, current=..., title=..., subtitle=..., owner=..., empty_text=...)`.
  Возврат — имя параметра или `None` при отказе.
- Элемент списка: строка либо `{u"name": ..., u"display": ...}`. В поле уходит `name`,
  пользователь видит `display` — туда пишут откуда параметр и насколько покрывает выбранные
  категории.
- Про Revit не знает: список готовит инструмент. Поиск фильтрует по `name`, двойной щелчок
  и Enter выбирают, Esc закрывает. `owner` — вызвавшее окно (иначе главное окно Revit).
- Принцип: кнопка ставится РЯДОМ с полем ручного ввода, а не вместо него — встроенные и
  семейные параметры в списки привязок не попадают, их всё равно вводят руками.
- Подключён в: «Передача параметров по MEP-соединениям», «Окрасить рандомно»
  (через ключ `choice.picker` в `pp_paint_dialog`), «Проверка спецификации»,
  «Проверка Модели», «Проверка теплопотерь» (через `option_type=u"param"`).

### `pp_param_source.py`
Единственное место, где список параметров собирается из модели (2026-08-19). Нужен, чтобы
`pp_param_picker` остался Revit-независимым, а инструменты не повторяли обход привязок.
- `project_parameters(doc)` → `имя -> {u"instance": set(id категорий), u"type": set(...)}`
  по `doc.ParameterBindings`.
- `project_options(doc, category_ids=None, instance_only=False)` → готовые строки для
  `pp_param_picker`: `ADSK_Группирование    · экземпляр / тип · 2 категории`.
  `category_ids` меняет хвост на «есть у N из M выбранных категорий» и поднимает полные наверх.
  `instance_only=True` убирает привязки типа — для инструментов, читающих значение через
  `LookupParameter` у экземпляра (иначе показали бы параметр, который они не прочитают).
- Встроенные и семейные параметры в привязки НЕ попадают: поэтому кнопка «Выбрать…» всегда
  дополняет поле ручного ввода, а не заменяет его.

## Панели и инструменты

Карточки сгруппированы по панелям. Шаблон карточки инструмента — в конце файла.

### 01_Инфо
- **Инфо** — информация о плагине (`script.py`, `icon.png`, `logo.png`). Справочная кнопка.

### 02_Настройки
- **Настройки** — UI настроек плагина. Читает/пишет через `pp_settings`. Точка управления
  всеми параметрами из `pp_settings.json`. Вкладка «Проверка» содержит настройки инструментов
  панели проверки, включая показ pyRevit-отчёта для передачи параметров по MEP.

### 03_Марки
Панель работы с марками. Опирается на `pp_tags`, `pp_leaders`, `pp_geometry`. Два стека.
Порядок кнопок задан тремя файлами сразу (`bundle.yaml` с ключом `layout:`, `_layout`, `layout`) —
имена в них = имена папок С числовым префиксом, без расширения; не перечисленные элементы не создаются.
Текущий порядок (после переноса «Сопоставить труб и возд.» к группе «Сопоставить», 2026-06-30):
- **01_Сопоставить** — сопоставление марок.
- **02_stack2.stack**: Сопоставить по семейству / Сопоставить по типу.
- **03_Сопоставить_марки_воздуховодов_труб** — перенесена сюда (была 11-й).
- **04_Копировать по типу**, **05_Копировать по семейству**.
- **06_Копировать марки для пары труб** — учитывает `pipe_pair_distance_mm`.
- **07_Копировать марки труб**.
- **08_Применить тип марки от эталона**.
- **09_stack3.stack**: Применить тип марки по типу / по семейству (переименован из stack2 в stack3 — имена стеков в одной панели лучше держать уникальными).
- **10_Копировать вертикальные воздуховоды и трубы авто**, **11_… (ручной)**.
- **12_Инструменты меток** — конфигуратор шаблона `tag_rules` (WinForms). Три зоны:
  список категорий (пока 2 — `CONFIG_ENUM_NAMES`: воздухораспределители, арматура возд.),
  `TreeView` семейств→типов ЭТОЙ категории из проекта (`collect_element_types`), справа
  `ComboBox` существующих марок категории (`collect_tag_symbols`). Кнопки «Назначить
  выделенному»/«Очистить» пишут правило на узел (семейство → `type=None`, тип → конкретный).
  Экспорт/импорт правил отдельным `.json` (сервер, брату). Сохраняет в `pp_settings.json`.
  Правила ДРУГИХ категорий в списке не трогаются (сохраняются как есть).
  С 2026-08-20 окно на WPF и с двумя режимами (чипсы под заголовком):
  «По семейству и типу» — прежнее дерево (уже БЕЗ воздуховодов); «Воздуховоды» — пресеты
  `tag_size_presets`. Во вкладке «Воздуховоды» три колонки: слева список пресетов с полем
  имени и кнопками «Создать/Переименовать/Удалить», в центре строки активного пресета и
  строка покрытия («не покрыты надписи длиной 5–6, 8» цветом `Hot`), справа редактор строки
  (на какие воздуховоды — все/семейство/тип, «от»/«до» знаков, марка) и блок `Card.Result`
  с предпросмотром и примером надписи такой длины. Диапазоны пересекаться не могут ВНУТРИ
  одной области; если сосед начинается раньше и упирается в новый диапазон — окно само
  подвигает его верхнюю границу и пишет об этом в статус.
  `ask_tag_rules(rules, categories, load_marks, load_types, size_presets, size_active)`
  возвращает словарь `{"rules", "presets", "active"}` (раньше — просто список правил).
  Экспорт пишет `{"rules", "presets"}`; импорт понимает и старый формат (голый список).
- **14_Применить по шаблону** — ГЛАВНЫЙ рабочий сценарий. Пользователь ставит марки родной
  командой Revit «Маркировать по категории», затем жмёт эту кнопку — скрипт находит марки
  (если что-то выделено — по выделению, иначе весь активный вид), по помеченному элементу ищет
  правило (`find_rule_for_element`) и меняет тип марки `ChangeTypeId`. По сути «Применить тип
  марки», но источник — шаблон, а не эталон. Отчёт: изменено / уже по шаблону / нет правила
  (точные имена) / тип марки не загружен.
  С 2026-08-20 сначала пробуется размерное правило активного пресета (`tag_size_active`):
  для воздуховодов читается `IndependentTag.TagText`, считается длина надписи и берётся
  строка пресета, подходящая по семейству/типу воздуховода и по длине. Старые правила
  `tag_rules` по воздуховодам вычищаются `strip_size_categories`; для остальных категорий
  всё как было. Если диапазон не подошёл — падаем на правило по семейству, если и его нет —
  марка пропускается. В отчёт добавлены: «из них по размеру надписи», активный пресет,
  «нет строки под такую длину надписи» и счётчик марок с нечитаемой (пустой) надписью.
  > Кнопку «13_Маркировать» размерные правила пока не трогают: она ставит марку, когда
  > надписи ещё нет. После расстановки достаточно прогнать кнопку 14.
  > Кнопка «13_Маркировать по правилу» (своя постановка по клику через `IndependentTag.Create`)
  > удалена как избыточная 2026-07-01 — рабочий путь только через родную команду + кнопку 14.

В окне инструмента пользователь выбирает категории источника и приемника из четырех вариантов: трубы, соединительные детали трубопроводов, арматура трубопроводов и оборудование, затем задает имя параметра источника и приемника. Режим обработки выбирается из четырех вариантов: «Вся модель», «Текущий вид», «Источник вручную», «Приёмник вручную». При ручном выборе источника Revit разрешает выбрать только элементы выбранных категорий источника; дальше приемники собираются только из напрямую подключенных к этим источникам элементов выбранных категорий приемника. При ручном выборе приемника Revit разрешает выбрать только элементы выбранных категорий приемника; источники при этом ищутся по их коннекторам. Скрипт смотрит только напрямую подключенные элементы через коннекторы Revit и переносит значение, если найден один источник или несколько источников с одинаковым значением. Если найдены разные значения, элемент попадает в конфликт; если заполненный источник не найден, элемент попадает в отчет «источник не найден». Значение источника читается сначала у экземпляра, затем у типа. Запись выполняется только в параметр экземпляра приемника, чтобы не менять сразу все элементы типоразмера. Стартовая конфигурация окна: источник = трубы, приемник = арматура трубопроводов, параметр = `ADSK_Имя системы сокращенное`. Последние имена параметров и выбранный режим сохраняются в `pp_settings.json` в ключе `mep_param_transfer_settings` (`mode`). Подробный вывод в окно pyRevit управляется настройкой `mep_transfer_show_pyrevit_report` на вкладке «Проверка» в инструменте «Настройки»; итоговая белая сводка показывается всегда.

### 11_Статистика
- **01_Статистика использования** — счётчик запусков инструментов плагина.
  - **Механизм: СВОЯ телеметрия (`lib/pp_usage.py`), встроенная телеметрия pyRevit
    больше не используется.** Отказались от неё 2026-07-20: она создавала файл на
    каждую сессию (67 файлов), но реальных записей почти не писала, логировала чужой
    `pyRevitCore`, а путь к папке сохраняла экранированным и молча отключалась.
  - Универсального хука «на любую кнопку» в pyRevit НЕТ (есть только
    `command-before-exec[<id>]` по конкретному id), поэтому вызов явный: в начало
    каждого `script.py` вставлена защищённая строка

        try: import pp_usage; pp_usage.log(__file__)
        except Exception: pass

    Она стоит сразу после строки кодировки. `pp_usage.log()` никогда не бросает
    исключений — сбой логирования не должен ронять инструмент.
  - **Формат: append-only JSONL** — `telemetry/pp_usage_YYYY-MM.jsonl` (одна
    JSON-запись на строку, файл на месяц). Выбран намеренно: дописывание строки
    атомарно, несколько сессий Revit не портят файл, битая строка не убивает весь
    лог (в отличие от единого JSON-массива, который вёл pyRevit).
  - Поля записи: `ts` / `date` / `time` (локальное время), `tool` (имя без префикса
    «06_»), `bundle`, `panel`, `tab`, `user` (**имя пользователя из настроек Revit**,
    через `HOST_APP.username`), `winuser`, `revit`, `doc`.
  - Разбор пути кнопки идёт вверх по дереву и корректно понимает кнопки внутри
    `.stack` (панель находится через уровень).
  - Кнопка статистики читает `pp_usage.read_records()` и показывает WinForms
    `ListView` с переключателем группировки: по инструментам / по пользователям /
    по инструментам и пользователям. Есть «Экспорт в CSV» (utf-8-sig, разделитель `;`).
  - **Правило для новых кнопок:** при создании любой новой кнопки обязательно
    добавлять строку `pp_usage.log(__file__)` — иначе её запуски не попадут в учёт.
  - **Хранение:** `telemetry/` внутри расширения; периодическая выгрузка на сервер
    (xpenology) — `export_telemetry.bat` (robocopy по маске `pp_usage_*.jsonl`) в
    корне расширения, ставится в Планировщик задач Windows (заменить `DST`).
  - Учёт ведётся с момента установки этой версии; задним числом данных нет.
  - **Грабля чтения (2026-07-24):** нельзя читать JSONL лениво через
    `for line in io.open(path, encoding="utf-8")` — в IronPython построчное чтение
    utf-8 с кириллицей срывается посреди файла с исключением. Если это исключение
    ловить на уровне ВСЕГО файла, теряются все строки после сбоя (симптом: в
    статистике видно только первые 1–2 записи, хотя в файле их сотни). Правильно:
    читать файл целиком в бинарном режиме (`io.open(path, "rb").read()`), декодировать
    самим (`raw.decode("utf-8-sig", "replace")`), бить на строки в памяти и парсить
    каждую в отдельном try/except. Сделано в `pp_usage._read_text` / `read_records`.
  - **Важно:** новая панель/кнопка появится в ленте только после
    `pyrevit caches clear --all` + запуск Revit (Reload не пересобирает ленту).
    Правки внутри `script.py` подхватываются сразу, без Reload.

## Принятые решения и нюансы

В WinForms-окнах размер задавать через `ClientSize`, а НЕ через `Size`.
`Size` — это размер окна целиком, включая заголовок и рамки (~40 px по высоте),
поэтому элементы, позиционированные у нижнего края (кнопки, подписи), обрезаются
границей окна. Правильно: `self.ClientSize = Size(w, h)` и все координаты считать
от `w`/`h`, например `btn_y = h - PAD - BTN_H`. `MinimumSize` при этом остаётся
размером окна — его берут с запасом. Наступили на это в «Статистика использования»
(2026-07-20), кнопки «Экспорт в CSV» и «Закрыть» оказались срезаны.


- Резервное копирование перед изменениями — обязательно (см. `AGENTS.md` → «Резервное копирование»).
- При правке Revit API проверяется вручную через pyRevit Reload.
- **Перестановка кнопок в панели (важно, проверено 2026-06-30):** порядок применяется только при создании ленты с нуля. pyRevit Reload создаёт кнопки с `update_if_exists=True` — обновляет существующие «на месте», НЕ переставляя; `sort_pyrevit_ui` переупорядочивает только панели, не кнопки внутри панели. Переименование папки кнопки двигает её при Reload (меняется unique_name → пересоздаётся), но переименование стека/правка `layout` — нет.
- **Главный нюанс:** структура расширения кэшируется pyRevit в `%APPDATA%\pyRevit\`. После правок раскладки (layout, стеки) одного Reload и даже полного перезапуска Revit мало — нужно очистить кэш: `pyrevit caches clear --all`, затем открыть Revit. Симптом устаревшего кэша — заголовок панели «прыгает» между `03_Марки` и `03 Марки`.
- Стек (`*.stack`) объединяет 2 кнопки вертикально — соблюдать при добавлении кнопок в группу.
- Иконки — строго по `ICONS.md` (32×32, PNG, прозрачный фон, имя `icon`).
